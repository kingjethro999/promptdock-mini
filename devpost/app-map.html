1. Request & data flow one screen, two POSTs

The whole app is one client component (app/page.tsx) owning top-level state, two POST routes, and a provider chain underneath. Nothing is fetched on page load; the only network traffic is the user's own shaping and building requests.

3. The two routes

POST /api/shape
  • Validates body → 400 invalid_body on malformed input.
  • Calls completeParsed() with SHAPE_SYSTEM_PROMPT; parse failure falls through the provider chain rather than surfacing.
  • Server-side ceiling: when questionCount ≥ MAX_QUESTIONS (3) the route forces needsFollowUp:false even if the model asks — double insurance beside the client's own payload.questionCount < 3 guard.
  • Response shape: route returns { interpretation: { fields }, needsFollowUp, question } (model JSON has top-level fields; the route nests them). Feeding route JSON back into parseShapeResponse() fails by design.
  • Providers down → 502 ai_unavailable.

app/api/shape/route.ts · lib/validate-shape.ts · lib/prompts/shape.ts

POST /api/build
  • Validates: thought 3–6000 chars, interpretation.fields (label/value strings, provenance default known, ≤40), answers ≤5 → else 400.
  • nothing to build from: zero fields and zero answers → 400.
  • Calls complete() — not json:true: the contract is free prose, not JSON.
  • Empty completion or all providers failed → 502 ai_unavailable, never a partial prompt (the failure branch can't leak half a result into the editor).
  • Route writes nothing: persistence is a client decision (a dock is written only when prompt actually arrives).

4. Provider-chain path

SymbolBehavior
providerOrder()Reads AI_PROVIDER_ORDER at call time (default apmix,groq,gemini), intersects with known providers, caps via AI_MAX_FALLBACKS.
runChain()Loops the order, one attempt per provider; records ProviderAttempt per hop; throws AiUnavailableError when the chain is exhausted.
postChat()Single HTTP call per provider with timeout (AI_REQUEST_TIMEOUT_MS); model chosen per provider from env (APMIX_MODEL, GROQ_MODEL, GEMINI_MODEL).
extractJson()Strips ```json fences — apmix and gemini wrap replies in them; groq returns bare JSON.
complete()Returns Completion {text, provider, model, latencyMs} — used by /api/build (prose).
completeParsed()Same chain but a parse failure counts as a failed attempt and falls through to the next provider — used by /api/shape.

Because every read of the environment happens at call time, tests can blank the keys in-process and watch the chain genuinely fail (that's how test-build-route.ts proves the 502 path). Measured behavior: apmix ≈5–8s, gemini ≈1.3s, groq ≈0.8s.

5. Prompt-contract files

  • lib/prompts/shape.ts — the system prompt that forces chips-as-JSON (fields[] with id/label/value/provenance), forbids placeholder values (unknown/missing/TBD/N/A), and defines when a single high-impact question is asked. buildShapeUserMessage() serializes thought + current interpretation + answers + questionCount + lastQuestion so every round re-evaluates the whole picture.
  • lib/prompts/build.ts — the system prompt that compiles thought + fields + answers into a finished coding-agent prompt. BuildModelInput is the exact shape the client sends; buildBuildUserMessage() is its single serialization point.
  • lib/validate-shape.ts — parseShapeResponse(): structural validation of model output (fields present, sane types) before anything renders.
  • lib/types.ts — the shared vocabulary both contracts compile against: Field/provenance, ShapeResponse, caps (MAX_QUESTIONS, MIN_THOUGHT_CHARS, MAX_DOCKS).

7. The promptEditedManually sync protection

This is the invariant the whole editor hangs on — the failure it prevents is generated → hand-edited → chip edit → your wording silently overwritten. The flag lives in app/page.tsx; PromptEditor emits change events upward rather than owning state, so slice 7 could persist it with the dock without touching the editor.

StateChip edit / reshapeNetworkStored flag
Untouched (just generated)Auto-regenerate immediately + transient ✦ Updated cue1 POST /api/buildfalse
Hand-editedUnderstanding changed. + Update prompt; prompt bytes untouched0 requeststrue (persisted per keystroke)
Update prompt pressedRegenerate from latest chips, banner clears1 POST /api/buildfalse
  • Single-flight for free: Interpretation is disabled while promptBusy, so the sync engine (event-driven, not a useEffect — an effect version deadlocked re-running on its own busy state) can't overlap requests.
  • Failure branches keep the invariant: a failed regeneration shows Couldn't update the prompt. and leaves the last good prompt byte-intact.
  • Reopened docks re-enter this table from the stored flag — a saved hand-edited dock is still protected after reload (verified with 0 regen calls).

8. Theme boot & hydration path

  1. Before paint: ThemeBoot inlines a tiny IIFE script into the document head — reads pmd.theme, sets data-theme on <html>. No flash of the wrong theme, and React never participates in this step.
  2. Hydration: the server snapshot reports light; the client reads the live DOM attribute via useSyncExternalStore — a MutationObserver on data-theme keeps them converged.
  3. Toggle: ThemeToggle flips the attribute and calls setTheme(); it does not read storage during render.
  4. Styling: components reference tokens only (bg-panel border-line text-fg text-muted bg-green); the dark root in globals.css swaps values (#12291d deep green-black, lime accent) — audit shows zero hardcoded colors outside the CSS.

9. The demo path, step by step

The exact route the video walks (scope.md: thought → understanding → correction → usable prompt):

  1. Type the lending-tracker thought → ThoughtInput (guard passes at 3+ chars) → handleSubmit() → runShape() → POST /api/shape.
  2. Chips appear → Interpretation renders only model-returned fields; at most one FollowUpQuestion sits beneath, Build prompt is absent while it's pending.
  3. Answer → handleContinue() → another /api/shape round (client stops after 3; server forces the stop regardless) → Build prompt renders.
  4. Build → handleBuild() → POST /api/build → prompt lands in PromptEditor and the first dock row appears.
  5. Correction: click a chip → edit → Enter → handleFieldChange() → untouched → runRegen() → prompt visibly changes, ✦ Updated flashes, the same dock updates.
  6. Copy → clipboard gets exactly the editor's bytes; no dock write.
  7. Aftermath: Recent docks row click restores everything; reload returns to the clean thought screen with list + theme intact.

11. A practice from this project worth reusing

Force the failure path in every verification, not just the happy path. Each slice's evidence includes a deliberately broken run: providers blanked in-process to prove the 502, route.abort() mid-request to prove a failed build leaves no partial prompt and no lost work, a simulated QuotaExceededError to prove storage failures don't kill a session, and a hand-edit followed by a chip edit to prove the sync rule holds under the exact condition it was written for. Happy-path tests only prove the app works when nothing goes wrong — the PRD's guiding principle (AI failure should cost the user time, never their work) is only demonstrable when the tests make the AI fail on purpose. The same habit applies to any project that calls a model: ship the forced-failure test alongside the feature.
