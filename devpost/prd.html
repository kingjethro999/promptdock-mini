Prompt Dock Mini — Product Requirements

A single-page tool that turns a messy, half-formed thought into a usable prompt by first showing its understanding in editable pieces, asking at most three questions when a wrong guess would matter, and compiling the result. Built for someone who wants a better prompt without learning to write one.

Screens and Layout

scope.md > The Core Loop, The Unique Kernel

One screen, not several: a single page that grows downward as understanding increases. No navigation, no wizard, no progress bar, no Back/Next, no sidebars, no separate review page.

Top to bottom, in order
  1. Header — wordmark left, theme toggle right. No nav links, account button, or help menu.
  2. Thought — heading, quiet supporting line, one large multiline input, Shape this, and the reassurance line. After shaping it compacts, is relabelled Your thought, stays editable, and resubmitting recomputes rather than preserving stale chips.
  3. What I understood — quiet heading, then chips for only the fields that apply (Goal, Audience, Context, Requirements, Output are illustrative, not a schema).
  4. Follow-up question — conditional, inline beneath the chips. Never a modal or chat window.
  5. Build prompt — conditional, rendered only when no high-impact question is pending.
  6. Your prompt — conditional: tall editable editor, Copy, plus Update prompt only when the prompt has been hand-edited and the understanding has since changed.
  7. Recent docks — conditional, beneath everything, rendered only when docks exist.

Features and Behavior

First screen
  • Header: wordmark + theme toggle. Nothing else.
  • Centered main content with a slight upper-center bias.
  • Heading "What are you trying to get done?", supporting line "Messy is fine."
  • Placeholder: "Describe it however it comes to mind…"
  • Examples are placeholder copy only — never clickable cards, templates, or suggestions.
  • Reassurance: "No perfect prompt needed. Start with the rough idea."
  • Shape this disabled below 3 non-whitespace characters (trimmed); enabled at 3+. No validation message at any point. No semantic or AI-based judgment of whether input is "good enough" — extremely vague input goes through.
  • Cmd/Ctrl + Enter submits.
  • The first screen presents exactly one obvious action: type into the box.
  • Shape this is disabled at 0–2 non-whitespace characters and enabled at 3+, with no error text shown.
Shaping
  • On submit: Shaping…, thought stays visible, duplicate submission blocked.
  • On success: thought compacts to an editable Your thought field with exact wording untouched; What I understood appears with chips.
  • Editing the thought and resubmitting recalculates the interpretation — stale chips are not preserved.
  • After shaping, the original wording is present and unmodified in the thought field.
  • Two different thoughts produce visibly different chip sets.
Interpretation chips
  • Known: plain chip, no icon. Inferred: same style, tiny sparkle, dotted underline, hover reveals "Inferred from your thought."
  • No loud color difference between known and inferred.
  • Clicking turns the value into an inline editable field. Manually editing an inferred value marks it known.
  • An inferred value shows sparkle + dotted underline and a hover explanation.
  • After hand-editing an inferred value, it renders as known with no inferred cue.
Follow-up questions — the Gap Rule
  • At most one question visible at a time, directly beneath the chips. Header: "One thing I need to know", with a Continue action.
  • After each answer: incorporate, update the interpretation, re-evaluate gaps, then ask the next question or reveal Build prompt.
  • Hard ceiling: 3 questions per dock. After the third, unresolved gaps become visible inferred assumptions and the flow continues.
  • Build prompt is not rendered while a question is pending — never disabled with unclear reasoning.
  • The interpretation stays visible and readable while they answer.
  • Never two questions on screen at once.
  • A fourth question is never asked; the flow proceeds with remaining gaps marked inferred.
  • Build prompt is absent while a question is pending, and appears once none is.
Build prompt
  • Strongest visual action in its state; all chips editable before pressing.
  • On press: Building…, interpretation stays visible with editing visually paused, duplicate generation blocked.
  • At most one generation request is in flight at a time.
Prompt editor and interpretation sync · the demo beat
  • A tall multiline editor that reads as the final artifact, directly editable. Minimal actions: Copy, plus Update prompt only for the out-of-sync case. There is no generic Rebuild prompt action in the POC.
  • Copy copies the current editor contents and briefly reads Copied. No toast pile, no modal, no persistence responsibility.
  • Sync rule — the single internal distinction is generated prompt untouched vs manually edited prompt:
    • Untouched: editing a chip auto-regenerates; the changed portion visibly updates and a brief ✦ Updated marker appears.
    • Manually edited: chip edits never silently overwrite. Show "Understanding changed." with Update prompt.
  • With the prompt untouched: changing a chip updates the prompt with no second Build prompt press, and an Updated cue is briefly visible.
  • After hand-editing: changing a chip leaves the hand-edited text byte-for-byte intact and shows "Understanding changed." with Update prompt.
  • Copy returns exactly what is currently in the editor.
Recent docks
  • Local storage only. Latest 10, newest first.
  • Written only on successful generation. Copy does not save. Regenerating an already-saved dock updates that dock rather than creating a second row.
  • Stores: thought, interpreted fields with provenance, follow-up answers, prompt, timestamp.
  • Rows show an auto-title + relative time; clicking one restores the editable state rather than forking a copy; quiet per-row delete.
  • Title rule (locked): Goal → else the first ~6 meaningful words of the original thought → else Untitled dock.
  • No rename, folders, tags, search, pinning, sync, or accounts.
  • With no docks, the section renders nothing at all — no empty state, no "You have no recent docks."
  • A dock appears immediately after first successful generation; regeneration updates the same row.
  • Reopening restores thought, chips, provenance, answers, and prompt as editable.
  • A dock with no usable Goal is titled with the first ~6 meaningful words of the thought; Untitled dock only when neither exists.
Loading and failure states
First generation fails Interpretation stays visible; inline "Couldn't build the prompt." with Try again and quiet "Your work is still here." No modal, no navigation, no dock written.
Regeneration fails The last good prompt stays intact and usable; inline "Couldn't update the prompt." with Try again. An error never replaces a working prompt.

Shape this → "Shaping…" · Build prompt → "Building…" · duplicate actions blocked throughout

States and Boundaries

Every state we specified
  • First use (no docks) — the page is the input; Recent docks renders nothing.
  • Empty input — Shape this disabled; no message.
  • Generation fails (first attempt) — see above; no dock written.
  • Regeneration fails — last successful prompt survives.
  • Processing — buttons relabel, duplicates blocked, nothing the user wrote disappears.
  • Persistence — browser local storage only, this device, this browser. Clearing site data removes docks; no recovery, sync, or export. Ten text-only docks are far below any quota that matters; if a write fails, the session continues normally — nothing is lost, the dock simply isn’t persisted for next time.
  • Who sees what — single user, single device, no accounts, no sharing. Nothing leaves the browser except the request that shapes and builds the prompt.
  • Locked rules — gaps never render as "missing"; 3-question ceiling; save on successful generation only.
Guiding principle: AI failure should cost the user time, never their work.

The Boundary

What we're building

The product requires AI inference. Shape this and Build prompt both call a model. How is a 4-spec decision; the standing constraint is that provider credentials never reach the browser — inference goes through server-side routes, so this deploys as one Next.js app with no separate backend service.

  • Single page, header + theme toggle, light/dark
  • Thought input, 3-char guard, Cmd/Ctrl+Enter
  • Known/inferred chips, inline edit, inferred → known
  • Inline questions, ceiling 3, then inferred
  • Build prompt + processing + inline recovery
  • Tall prompt editor, Copy + Update prompt
  • Chip → prompt sync (untouched vs edited)
  • Recent docks: local, cap 10, save on generation, restore, auto-title, delete
  • Both error states
  • Survives a browser reload
Deferred from the POC
  • Accounts, sync, sharing — one browser proves continuity without a backend
  • Running the prompt — a 1.0 feature, drags in keys, models, cost
  • Model/provider selection and BYOK
  • Multi-agent pipeline / execution view
  • Template gallery, onboarding, marketing copy
  • Library management — rename, folders, tags, search, pinning
  • A visible "missing" chip — three states is a questionnaire; two is a product
Possible later enhancements
  • Manual dock renaming and pinning, once ten rows isn't enough.
  • Export a dock as a file, or share by link.
  • Alternate generations for one thought (several candidate prompts) — the only thing that would bring a generic rebuild action back.
  • Multiple dock slots per thought (variants) now that the sync rule exists.
  • Running the prompt, with provider choice.
Non-goals
  • No accounts, auth, or sync — no infrastructure to maintain for a demo.
  • No executing the prompt — scope.md > Explicitly Cut.
  • No wizard, progress bar, numbered steps, Back/Next, or sidebars.
  • No purple/blue AI gradients, glow, glassmorphism, neon, or floating sparkles.
  • No success screen, score, or completion step — the prompt is the proof.
  • No AI-based validation of the user's input — "Messy is fine."
  • No silent overwrite of a hand-edited prompt.
  • No generic Rebuild prompt action — the untouched path regenerates itself; the edited path has Update prompt.
  • No client-side provider key — inference goes through server-side routes so the key never ships to the browser.
Open questions

None. Three candidates were raised in review; all three are settled:

  • Storage quota — resolved: not a product concern at ten text docks; a failed write fails gracefully without losing the session.
  • Auto-title fallback — resolved: Goal → first ~6 meaningful words of the thought → Untitled dock.
  • Rebuild vs Update — resolved: Rebuild prompt is cut. Untouched prompts regenerate automatically; hand-edited prompts get Update prompt.
